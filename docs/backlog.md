## B1. 审计持久化（当前：内存环形 100 条）

- **现状**：`history` / `revert` 的审计记录只存在插件内存里；插件重挂或 App 重启后清空。
- **影响**：重启后无法回滚之前写入的配置；审计不可作为跨会话的"账本"。
- **适用场景判断**：日常"改完发现不对立刻回滚"不受影响；真正的缺口是"改坏了导致必须重启，重启后找不到回滚记录"这种最坏情况。
- **解法**（约 3–4h）：用官方 `storageDomain` + 自有 domain（`defineDomain` + zod schema），需给插件新增 peerDependencies：`@deepseek-ai/dsh-storage-domain`、`zod`（已确认 Desktop 安装区自带这两个包）；打不开 domain 时回落内存并如实告知。
- **低成本的过渡缓解**（约 10 分钟，可先做）：写入成功后，在结果里输出**可手工粘贴的恢复片段**（写入前的覆盖值 + 操作步骤），这样即使审计丢了也能照着改回去。

## B2. 审批策略是插件级，不是按行

- **现状**：只有 `approval: ask`（每次写入都要批准）或 `never`（只读）两个总开关。
- **影响**：不能"无害的行免审批、危险的行强制审批"；每次改配置都要点一次同意。
- **解法**（约 1–2h）：配置加 `approvalRows`（行 id → `ask|auto`），默认 `ask`；工具按行解析策略；测试覆盖 auto/ask/never 三种组合。
- **优先级**：低（日常改配置频次低，点一次同意成本可接受）。

## B3 执行记录（2026-11-09 21:5x 真机）

- **做了什么**：对 `workbench` 行做了一次真实、可回滚的写入（`requirePreview: false`），然后 `reset` 复原。
- **结果**：
  - 预览 → 凭证 `d11c02158b43c260` → apply → **真实写入成功**，覆盖值变成 `{"requirePreview":false}`；
  - 审批链路真实走通：`approval.request` 被调用并返回 `allowed-once` 后完成写入；
  - 写入后立即 `history`：**空**（见下）；`reset` 预览 → 凭证 → apply → 覆盖值恢复 `{}`，最终 `get` 确认回到初始状态。
- **重要发现（B1 的现场证据）**：
  - 修改的是 `workbench` **自己这一行** → 写入触发该行 fiber 重建 → 插件实例被销毁重建 → **审计记录当场清空**；
  - 所以"改自己这行"时，`revert` 实际上不可能用（连刚写的那条记录都没了），只能用 `set/reset` 手工复原。
  - 对**其它行**的写入不会重建本插件实例，审计会保留；但由于没有持久化，插件重挂/重启仍会丢。
- **关于"人工点击同意"**：本部署的审批回答者是自动审查（auto-review，LLM）而不是人工弹窗，这次是自动批准（`allowed-once`）；所以"真人点同意"这个具体交互没有发生。若要验证人工弹窗，需要临时调整审批回答者配置（部署级，不建议为测试改）。
