# 第二批（2026-11-09 晚）：跨会话新原语 — cursor / read(after) / wait(until)

> 目标：让"一个会话里的 Agent 指挥另一个会话干活并可靠取回结果"真正可用；不照抄竞品 15 个工具，只做 3 个原语。
> 验证：逻辑 **359/359**、schema **64/64**；真机（当前插件）已验证 `read(after)`、`wait` 空闲、`wait` 超时三条路径。

## 新增语义

| 原语 | 行为 |
|---|---|
| **cursor** | `send` / `steer` / `start` / `read` / `wait` 都返回 `cursor`（事件 seq 锚点）。`start` 返回 -1（空日志）。 |
| **read({ after })** | 只读 `after` 之后的事件（前向增量）；返回新 `cursor`。缺省仍读最近 N 条（向后翻页用 `beforeSeq`）。 |
| **wait({ after, until, timeoutMs })** | `until: 'done'`（默认，整轮结束）\| `'reply'`（新的完整助手回复）\| `'step'`（完成一步：工具结果或回复）。**超时不抛错**：返回已收到的事件 + `cursor` + `idleForMs`。 |
| | 不带 `after` 时以"调用时刻的日志末尾"为基线，不把历史事件当新内容。 |

## 实现要点

- `logEndSeq()`：投递前读日志末尾 seq 作为 cursor（官方 `controller.events`）。
- `readEventsAfter()`：前向读，必要时向更早翻页覆盖窗口（最多 40 页），去重按 seq 升序。
- `waitForNewEvents()`：基于官方 `session/event` 订阅；catch-up 先补已发生事件；`reply`/`step`/`turn/end` 任一条件到达即返回；50ms 状态兜底 + 超时兜底。
- 工具描述追加 CURSOR 段落（放在描述尾部，前 240 字符不变）；schema 新增 `after`（read/wait）与 `until`（wait）参数。

## caveat 2 的解决方案：把"日志不落盘"换成"降级路径可断言"

`logger.warn` 不落盘 → 不能靠翻日志证明"静默失败都被优雅处理"。做法：**不依赖日志，直接断言行为**。

1. 假 ctx 的 logger 现在**记录**所有 warn（`world.warnings`）；
2. 增加故障注入开关 `world.faults`（`titles` / `querySessions` / `controllerList` / `privateSummary`）；
3. 新增 6 组降级用例、共 12 条断言，覆盖全部关键静默失败路径：
   - 标题批量读失败 → `list` 仍返回行（标题降级），记 `session titles unavailable`；
   - `ctx.emit` 抛错（播报失败）→ `pin` 仍成功，记 `announce failed`；
   - 公开 `controller.list()` 失败 → 回落私有路径，`pin` 仍成功，记 `list summary failed`；
   - 私有 `summaryFor/summarizeCold` 也失败 → 仍不阻塞，记 `private summaryFor failed`；
   - `fork` 后登记工作区失败 → fork 成功且文本如实说"未分组"，记对应 warn；
   - 配置工具查活动会话失败 → 配置 list 仍返回内容，记对应 warn。

**测试结果：逻辑 374/374，schema 64/64。** 含义：发布前不需要"日志里零 warn"这种不可控证据，而是有确定性的"失败路径 → 降级行为 + 预期 warn"断言。

## 附：官方 pin 的 UI 语义（回答"置顶为什么在未分组里"）

核对 0.2.2-rc.1 官方 client 源码（`@deepseek-ai/dsh-client-ui-workspace/lib/client.js`）：

- `pinnedSessionIds` 是**全局**的置顶集合（工作区注册表的 global state：`workspaceIds` / `archivedSessionIds` / `pinnedSessionIds`，pin 数组最近置顶在前）；
- 但**渲染**不是"全局置顶区"，而是：**置顶会话在它所属的分组（或"未分组"）内部排最前，同时在扁平列表里排最前**。
  源码注释原文：*"The accounts a pinned Session leads: its group (or Ungrouped) and the flat list."*、*"pinned rows leading in the selected local order"*。
- 结论：置顶出现在「未分组」分组内部的顶部，是**官方预期行为**，不是 bug。

## caveat 1 结论

真机置顶行为正常（行渲染 + 置顶标记 + 标题正常），临时会话（`补帧验证-2010`）已 unpin + archive + 删除 `/tmp/dsh-verify2`。

## caveat 2 方法论说明（业界对照）

"故障注入 + 行为断言"属于业界标准做法，通常叫 **failure injection / error-path testing / resilience testing**：

- 代码/库级别：stub 依赖并让其抛错，断言两条——**调用方优雅降级** + **告警被记录**（我们做的就是这一层）；
- 分布式系统级别：同一思想放大成 **chaos engineering**（Netflix Chaos Monkey / Gremlin 等），在受控环境注入真实故障；
- 与日志的关系：日志是**运行时可观测性**（用于发现和告警），测试是**发布前证据**（用于证明行为），业界把两者当互补，而不是互相替代——所以"日志不落盘"不妨碍用测试证明降级行为。

边界（诚实）：这种测试证明的是"我们的代码在依赖失败时如何表现"，不证明"真实服务在真实故障下的表现"；后者需要集成/契约测试或 staging 灰度。对本插件这个量级，当前做法是相称的。
